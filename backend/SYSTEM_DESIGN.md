# System Design Write-up

## Double-booking prevention
The naive approach — "check if slot is free, then insert" — is unsafe under concurrency: two requests can both pass the check before either inserts, producing two bookings for the same slot. This system instead relies on a **database-level unique constraint**: `@@unique([doctorId, slotStart])` on the `Appointment` table. The availability check (`GET /doctors/:id/slots`) is only used to *render* options to the user; the actual guarantee comes from the `INSERT` itself. If two patients race for the same slot, Postgres accepts the first `INSERT` and rejects the second with a unique-violation error (code `P2002`), which the central error handler converts into a clean `409 Conflict` telling the second patient to pick another slot. This is correct regardless of request timing, server instance count, or network delay — properties that in-app mutexes or "check-then-write" logic cannot guarantee once the app is horizontally scaled.

## Slot generation and holds
Slots are generated on-demand from `DoctorProfile.workingHours` (a JSON map of day → `[start, end]`) and `slotDurationMin`, then filtered against two things: existing `BOOKED` appointments for that date, and `DoctorLeave` rows. No slot is persisted until a booking actually happens, which avoids maintaining and garbage-collecting a separate "slot" table. The trade-off is that slot generation is computed per-request rather than cached — acceptable at clinic scale (a handful of doctors, tens of slots/day each); at larger scale this would move to a materialized, periodically-refreshed slots table.

The system does not implement a separate temporary "hold" (e.g., reserving a slot for 5 minutes while a patient fills the symptom form) because the unique constraint already makes the final booking step atomic and instant — a hold mechanism mainly matters when checkout has multiple steps with payment, which this flow doesn't have. If added, a `SlotHold` row with a short TTL (checked and cleaned by a cron job, similar to the existing reminder job) would be the natural extension.

## Doctor leave conflict handling
When an admin marks a doctor on leave for a date, `addLeave()` does three things in sequence: (1) inserts the `DoctorLeave` row so that date stops appearing as bookable going forward, (2) queries all existing `BOOKED` appointments for that doctor on that date, and (3) for each affected patient, cancels the appointment, sends a `LEAVE_CONFLICT` email, and deletes both patient- and doctor-side Google Calendar events. Each patient is processed in its own `try/catch` so that one failure (e.g., a bad calendar token for one patient) does not stop the remaining patients from being notified — reliability here matters more than atomicity, since a booking that silently stays "confirmed" while the doctor is on leave is worse than a partially-completed notification sweep that can be reconciled from the `Notification` table's status field afterward.

## Notification failure handling
Every outbound email — booking confirmation, cancellation, leave conflict, medication reminder — is first written to the `Notification` table with `status: PENDING`, then an actual send is attempted. If the send succeeds, status becomes `SENT`. If it fails (SMTP timeout, provider outage, invalid address), status becomes `FAILED`, `attempts` increments, and the error is logged, but **the triggering action itself never fails** — a patient booking an appointment gets a 201 response and a confirmed appointment even if the confirmation email temporarily can't be delivered. A separate cron job (`emailRetryJob`, every 10 minutes) re-queries `FAILED` notifications with `attempts < 5` and retries them using the same template functions, capping retries so a permanently bad address doesn't loop forever. This decouples "did the booking succeed" from "did the email send," which is the correct failure boundary for a system where email is a side effect, not the primary transaction.

## LLM failure handling
Both LLM calls (pre-visit urgency triage, post-visit summary) are wrapped in try/catch with Zod schema validation on the parsed response. Gemini's JSON mode (`responseMimeType: "application/json"`) removes most formatting failures, but schema validation still guards against the model returning an unexpected shape (e.g., an invalid urgency string). On any failure, a safe fallback object is returned instead of throwing — critically, urgency defaults to `"Medium"` rather than `"Low"`, since silently under-triaging a genuinely urgent case is the worse failure mode. The Appointment row records `preVisitLlmFailed` / `postVisitLlmFailed` booleans so failures are auditable rather than silent, letting a doctor or admin see which visits need manual review of the symptom text.

## Database schema rationale
A single `User` table with a `role` enum (rather than separate Patient/Doctor/Admin tables) keeps auth simple — one login path, one JWT shape — while `DoctorProfile` holds doctor-specific fields as a 1:1 extension. `Appointment` is the central table carrying both pre- and post-visit LLM output as JSON columns rather than separate normalized tables, since this data is read as a whole (never queried field-by-field) and doesn't need relational integrity beyond the appointment itself.
